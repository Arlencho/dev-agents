## 1. Plan summary

Build **Hermes**, a standalone messaging gateway that lets a signed-in user talk to Atlas from a messaging app (Telegram for the pilot, WhatsApp later), text only, inbound, with payment via a Stripe-scoped pay link. Telegram identity binds via an authenticated deep-link handshake (no OTP); OTP is deferred to the WhatsApp track. User-facing name: **Concierge** (Hermes is internal-only, never in UI). Hermes is a separate deployable service that talks to Olympus only through the public API. The reasoning engine (Conductor, via `POST /api/v1/parse`) is unchanged: Hermes is a second renderer on the same endpoint.

**Scope of this plan: v1 only.** Explicitly out: B2B, outbound alerts, voice, WhatsApp-as-launch. Kept as vision.

## 2. Location decision (locked for this plan, revertible)

Hermes lives at **`services/hermes/`** in the olympus-platform monorepo: its own Go module, Dockerfile, and Cloud Run service (so the failure-isolation the proposal promises holds), but co-located so it inherits repo CI and existing agent directory scopes. Matches the `services/` workspace pattern from the Go/Python ADR (#1855).

## 4. Wave 0 - the spike (de-risk, single agent, ~2-3 days)

`go-backend` stands up a throwaway Hermes against Telegram: hardcoded test user → `POST /api/v1/parse` → render `ai_message` back to the chat. No web, no auth, no DB, no migration. Throwaway branch, not for merge.

**Gate (human, Arlen):** a real Telegram message gets a real Atlas reply end to end. If yes, commit to Waves 1-3. If the loop is janky, we learn it here for the price of 2-3 days.

## 5. Wave 1 - the contract (merges FIRST, everything depends on it)

Dispatch order within the wave: QA writes contract tests first, then api-designer + db-architect in parallel.

- **api-designer + api-critic:** add `source` (`web|telegram|whatsapp|ios|android`) to the `/parse` input; the connect-token endpoints (mint on web "Connect" tap: 128-bit random, 10-min TTL, single-use, bound to the authenticated user; redeem via the narrow internal auth-lookup with a scoped service token, returning a short-lived user token); regenerate the TS client. `make generate`. (Proposal §6.1.)
- **db-architect + database-critic:** the **`channel_bindings`** table, channel-generic from day one: `(channel, external_id, user_id, consented_at, created_at, revoked_at)` where `external_id` is `chat_id` for Telegram, phone for WhatsApp later. Plus the `source` column on the persisted rows. **Migration numbered against merged `main`, not just open PRs (see #1897 - the exact trap #1777 hit).** (Proposal §7.)

**Merge rule:** api.yaml/contract merges before any Wave 2 work starts.

## 6. Wave 2 - parallel build (all dispatched at once)

Each task: QA test-first → producer → critic (opus, different model) → Security → CTO gate.

- **go-backend + backend-critic:** the real Hermes service. Channel I/O (Telegram), identity resolution via the Wave 1 lookup, `conversation_id` bookkeeping per thread, and the **text-mode rendering** of the Conductor clarify structs (`ai_message`, `date_clarify`, chips → plain text / "reply 1, 2, 3"). This is the craft-heavy task. Plus the API-side auth-lookup handler. Hard acceptance criteria (proposal §8, §9, §11, §14.1):
  - Per-chat ordered queue (serialize per conversation, never globally); instant webhook ACK + async processing; `update_id` dedupe with 24h memory; failure copy after 2 retries with backoff, never silence.
  - Cost controls: EUR 10/month per-user LLM budget metered on token cost, alert at 80%, graceful copy at 100%; 10 msg/min burst limit; unregistered chats get exactly one canned connect reply and **zero LLM calls**.
  - Copy set from proposal §11: media decline, group refuse-once-then-silent (DM-only), API-down, budget-reached. Copy is spec, not improvisation.
  - Emit the analytics events of proposal §14.1 (connect funnel, message, outcome, friction, demand).
- **web-frontend + frontend-critic:** the **Concierge settings section** (proposal §5): Telegram Connect tile, WhatsApp/iMessage coming-soon tiles (standard PRD §15 treatment), the "More channels" request tile, GDPR purpose-specific consent step (§6.3), deep-link + QR rendering, connected-state with handle display, and Disconnect (also the pilot kill-switch). **No OTP work** (deferred to WhatsApp track). PRD page for the section rides in the same PR.
- **devops:** `services/hermes/` Dockerfile, Cloud Run service, deploy pipeline entry, entrypoint assertion, and wiring Hermes into the existing spend-alerts (fleet-level LLM cost alarm).
- **security-reviewer:** red-team the identity binding (number recycling / SIM-swap / code-replay on the handshake) before any merge.

## 7. Wave 3 - pay-link + controlled pilot

- **The Stripe-scoped pay-link handoff.** Prerequisite: **#1121 (webhook confirms fail-open without amount check) closed first** - per § 9.3 of the proposal, the pilot must not ship on a fail-open confirmation path. Pick the Stripe primitive (Payment Link vs Checkout Session vs hosted PaymentIntent).
- Burst limit + budget metering on, disconnect kill-switch verified.
- Onboard a handful of known pilot users. **The pilot is judged against the success criteria in proposal §14.2** (connect <60s for 8/10, 5 full search exchanges, 1 real pay-link booking, zero duplicates/leakage/identity incidents, p95 <10s) with its explicit verdict rule: all pass → WhatsApp planning; identity or payment failure → stop.

## 8. Merge rules (repeated for agent clarity)

1. **Wave 1 contract merges before Wave 2 starts.**
2. Every PR: QA test-first → producer → critic (different model) → Security → CTO gate.
3. Migration numbers validated against merged `main` (#1897).
4. Wave 3 blocked until #1121 lands.
5. Hermes talks to Olympus ONLY through the public API (+ the one narrow auth lookup). No internal-package imports, no direct DB access. This is the isolation invariant; a critic must reject any PR that breaks it.

## 9. Risks and watch-outs

- **Text-mode fidelity** (Wave 2, go-backend): the most likely thing to feel rough; the spike surfaces the worst cases early.
- **Identity binding** (Wave 2, security): highest-value security surface; must prove number ownership so a recycled number can't hijack.
- **Scope creep**: WhatsApp / voice / outbound / B2B each multiply complexity. This plan is Telegram / text / inbound / consumer. Guard the boundary.
- **Isolation drift**: the moment Hermes reaches into the DB or shares the API process, the failure-isolation is lost. Invariant #5 above.

## 10. What is NOT in this plan (kept as vision)

WhatsApp launch, outbound alerts (need a live flight-status/price pipe), voice notes + calls, and the B2B corporate concierge (a separate product with org/policy/billing layers). Named here so they do not creep into v1.

**v1.5 fences (designed, deliberately deferred, proposal §12):** the web→Telegram trip picker (`/trips`), the budget refill/top-up mechanism, multiple parallel trips per thread. The metering ledger and conversation keys are built so these are additive later.
